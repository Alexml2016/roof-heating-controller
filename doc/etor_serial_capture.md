# Автоматическая регистрация ETOR-55 через UART: первый этап

**Состояние: подготовлен сборщик на Mac; прошивка ещё не дополнена.**
Настоящая программа испытаний: [T-29](technical_specification_and_test_plan.md).
Сборщик: [capture_etor_serial.py](../tests/capture_etor_serial.py).

## Почему выбран UART

WT32-ETH01 уже передавал журнал ESPHome через адаптер PL2303, порт macOS \`/dev/cu.usbserial-210\`, скорость 115200 бод. Поэтому для начальной лабораторной отладки достаточно последовательного порта; не нужно заранее знать IP или настраивать авторизацию Home Assistant. **Но** необходимо, чтобы ESPHome публиковал структурированные строки по окончании *каждого нового полного цикла измерения*.

## Необходимое изменение ESPHome

В \`alarm-roof-gateway.yaml\` после завершения прямого и обратного измерений электродов нужно выводить диагностическую строку с точным префиксом \`ETOR_SAMPLE:\` и JSON-объектом. Значения должны поступать из **реальных** измерительных переменных прошивки, а не из этого примера:

\`\`\`text
ETOR_SAMPLE:{"seq":34,"adc_a_forward_v":1.1,"adc_b_forward_v":2.2,"adc_a_reverse_v":2.3,"adc_b_reverse_v":1.2,"metric":0.7,"actual_state":"DRY"}
\`\`\`

Все числа в строке **условные** и приведены только для описания формата. Обязательные поля:

- \`seq\` — целочисленный номер нового **полного измерительного цикла**, увеличивающийся на 1 при каждом выполнении; одинаковые номера повторно не регистрируются.
- \`adc_a_forward_v\`, \`adc_b_forward_v\`, \`adc_a_reverse_v\`, \`adc_b_reverse_v\` — измеренные напряжения GPIO35/36 в вольтах, конечные значения.
- \`metric\` — вычисленная диагностическая величина (конечное число).
- \`actual_state\` — вычисленное **прошивкой** \`DRY\`, \`WET\`, \`SHORT\`, \`FAULT\` или \`UNAVAILABLE\`; может временно отсутствовать, тогда классификация будет \`BLOCKED\`.

**Иллюстрация интеграции с C++ в ESPHome после завершения цикла, не готовая вставка в неизвестный YAML:**

\`\`\`cpp
// Используйте реальные переменные только после проверки действительного YAML.
// Не включайте управление нагревателем/контактором при работе тестового режима.
// seq должен увеличиваться после каждого полного цикла с измерениями обеих полярностей.
ESP_LOGI("etor_bench",
  "ETOR_SAMPLE:{\"seq\":%u,\"adc_a_forward_v\":%.4f,"
  "\"adc_b_forward_v\":%.4f,\"adc_a_reverse_v\":%.4f,"
  "\"adc_b_reverse_v\":%.4f,\"metric\":%.6f,\"actual_state\":\"%s\"}",
  seq, a_fwd, b_fwd, a_rev, b_rev, metric, state);
\`\`\`

Названия переменных \`seq\`, \`a_fwd\`, \`b_fwd\`, \`a_rev\`, \`b_rev\`, \`metric\`, \`state\` в примере не привязаны к реальной конфигурации. Нельзя просто вставить блок без редактирования и считать его компилируемым. Нужно получить актуальный \`alarm-roof-gateway.yaml\` и проверить физические подключения \`CFG/485_EN\` к WT32-ETH01: конфликт GPIO17/GPIO32 ещё не разрешён.

Логи должны содержать одну строку JSON на один завершённый цикл. На ESPHome \`logger:\` должен быть включён вывод на UART с уровнем INFO либо более подробным. Обычный текст ESPHome сборщик игнорирует.

## Порядок работы на Mac

Сначала убедитесь, что силовые цепи и цепь 24 В нагревателя ETOR отключены. Подключайте резисторы **только вместо измерительных электродов A и B**, предварительно обесточивая устройство.

\`\`\`bash
cd ~/git-reps/roof-heating-controller
git pull
python3 -m pip install pyserial
python3 tests/capture_etor_serial.py \
  --port /dev/cu.usbserial-210 \
  --samples 10 \
  --output results/etor_run.csv
\`\`\`

1. Программа просит установить первый резистор и ввести измеренное мультиметром сопротивление (Enter — известный номинал; для обрыва оставить пустым).
2. После подачи питания на плату нажмите Enter для начала регистрации.
3. Скрипт пропускает строки без \`ETOR_SAMPLE:\` и дубликаты \`seq\`, записывает 10 **новых** полных циклов. Не берёт старые показания HA и не создаёт фиктивные.
4. Обесточьте плату, замените резистор, снова включите питание и нажмите Enter для следующего этапа.
5. После сбора всех значений запустите проверку:

\`\`\`bash
python3 tests/check_etor_simulation.py results/etor_run.csv
\`\`\`

Если прошивка не поддерживает отдельное состояние \`SHORT\`, тест КЗ останется \`BLOCKED\`, даже если напряжения записаны корректно. Если нет свежих циклов или нужного поля — \`BLOCKED\`, а не \`PASS\`.

**Первые испытания можно сократить до двух резисторов:**

\`\`\`bash
python3 tests/capture_etor_serial.py \
  --port /dev/cu.usbserial-210 \
  --cases dry_2m2,wet_47k \
  --samples 10 \
  --output results/etor_trial.csv
\`\`\`

Обычная проверка \`check_etor_simulation.py\` для такого неполного прогона закономерно вернёт \`BLOCKED\` по остальным случаям. Для предварительного знакомства с форматом см. \`tests/fixtures/etor_serial_demo.log\` — это **искусственные тестовые строки**, никогда не используйте их как натурные результаты.

## Что остаётся до запуска стенда

1. Опубликовать (без секретов) или передать текущий \`alarm-roof-gateway.yaml\`.
2. Проверить на собранной плате фактическое соответствие цифровых линий возбуждения электродов и АЦП. Ранее отмечено, что GPIO32/GPIO17 могут не быть выведены на фактическом WT32-ETH01 — нельзя назначать их предположительно.
3. Вставить JSON-логирование в точку завершения полного измерительного цикла.
4. Собрать и прошить ESPHome; проверить одну строку \`ETOR_SAMPLE\` в обычном журнале \`miniterm\`.
5. Провести два первых теста на 2,2 МОм и 47 кОм, затем полный T-29.
